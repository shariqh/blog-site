The first time I lost something important in terminal scroll, I shrugged. Claude Code had flagged an assumption about a database migration, buried two hundred lines above where I was looking, and I missed it. I caught it in code review, which is what code review is for, so no harm done.

The second time cost me forty minutes. I was running Claude Code across one repository and GitHub Copilot CLI in another, switching contexts every few minutes. Copilot had asked a clarifying question, I tabbed away, and by the time I came back the assumption it made in my absence was wrong. The model had made a reasonable guess and kept going, which is what models do.

After the third incident I stopped calling it a pattern and started calling it a design problem.

Chat interfaces are built for conversation, not for maintaining a durable record of the moments that need your attention. When you're running one agent, the cognitive overhead is manageable. When you're running two or three sessions across different tools and repositories, the signal that matters is indistinguishable from the noise around it, unless something routes it somewhere you can actually find it.

That's the gap a coding agent inbox was built to fill.

## What Agent View covers, and where it ends

Claude Code ships an Agent View that surfaces blocked status and pending decisions for Claude Code sessions. This is useful and I use it regularly. Agent View does what it says. Two things fall outside its scope by design. Sessions from other tools don't appear in it, and neither does the non-blocking signal category.

If you're also running Copilot CLI, or an agent built on a different SDK, those sessions don't appear in Agent View. And even within Claude Code, there's a category of non-blocking signal worth capturing. The workaround a model quietly applied, the tech debt it noted, the assumption it made without stopping to ask, the milestone it passed. That signal isn't noise, but it doesn't require a decision, so it has nowhere useful to go.

Agent Inbox sits alongside Agent View rather than replacing it. The cross-project queue is the central thesis. Any configured agent can flag an item or update a board in it, regardless of which SDK or CLI produced the session.

## The architecture is deliberately small

The first design constraint I set was no second model. Agent Inbox adds no AI. It's infrastructure built around the intelligence that's already running. That framing kept the scope honest and the implementation tractable.

The core is a user-scoped stdio MCP server. Agents connect to it the way they connect to any other MCP tool server, by calling tools like `flag` and `status` with a structured payload. The server reads from stdin and writes to stdout. It makes no network calls of its own. An agent running in a sandboxed environment with restricted outbound access can still flag an item without friction.



Every flagged item and board row lands in a single SQLite database at `~/.agent-inbox/inbox.db`, in WAL mode. WAL mode means the Hono viewer can read while agents are actively writing, without contention. The database is shared across every agent session on the machine, which is how the cross-project view works, not through network aggregation but because every agent writes to the same local file.

Project, branch, and client are inferred lazily from the environment when an agent calls a tool; a `register` call overrides the inference when it's wrong. The viewer is a Hono server bound to loopback only, with the same plain JavaScript frontend wrapped in Electron for a desktop experience. No browser tab to manage, no port to remember. Live PR state, when you want it, is fetched by the viewer through the local `gh` CLI and never enters the MCP server process.

## What a coding agent inbox should capture

The tool agents actually call is `flag`, and it takes three kinds: `question`, `note`, and `done`.

A `question` is blocking. It creates a row marked as waiting, surfaced with direct response choices so you can answer from the inbox without switching to a terminal. The agent polls `pending`, picks up the response, and calls `resolve` once it has acted on it.

`note` is the catch-all for everything non-blocking: an assumption the agent made without asking, a workaround it took and wants on record, tech debt it noticed, a caveat worth flagging. None of that stops the agent, and none of it belongs in `question`. `done` marks a completed milestone, worth announcing sparingly, not for routine progress.

One-shot flags aren't the whole surface. For a multi-item effort, a rollout checklist, a review queue, a migration's file list, the same agent keeps one titled tracking board alive with `board_upsert`, `board_row`, and `board_advance`, so the human watches standing status instead of a scroll of individual flags.

Live presence works the same way: no heartbeat. The agent calls `status` at real phase changes, starting a task, spawning subagents, wrapping up, and the viewer shows it live. Call it on a timer and you get noise instead of signal; skip it for too long, roughly half an hour with no MCP call at all, and the claim quietly reverts to idle. A glance at the inbox tells you whether an agent is still running without going back to a terminal.

## The reporting contract is half the product

Shipping the store was the easier part.

The harder problem is teaching agents when to use it. An MCP tool is just a callable surface; the agent decides whether to call it and when. Flag too aggressively, and the inbox fills with noise. Flag too conservatively, and the inbox is empty and you're back to watching scroll. The filing discipline is what determines whether the queue is useful.

The reporting contract I settled on lives in the agent's system prompt, the same fragile place [I've relied on before for behavioral rules](/blog/hooks-not-vibes-deterministic-guard-rails) and learned to distrust once context gets long. It gives the agent a taxonomy of when each `flag` kind is appropriate, with concrete examples. A `question` is warranted when the agent cannot proceed without a decision that changes the scope or direction of the task. Everything else non-blocking becomes a `note`: an assumption the human didn't explicitly authorize, a workaround the agent knows is suboptimal and wants a record of, tech debt worth surfacing. The agent exercises judgment about what's worth logging; the contract gives it the frame to reason within.

Getting this right took more iteration than any other part of the project. An early version of the prompt produced too many questions. Models are well-trained to ask before acting, and given latitude they'll surface things that genuinely don't require a human in the loop — whether to create a helper function or inline the logic, say. Tightening the definition of when a `question` is warranted, and being explicit that `note` exists for everything that doesn't require a decision, changed the behavior significantly.

The contract is still evolving. The lesson I keep returning to is that a queue without a filing discipline is just another pile. The reporting contract is what turns the MCP server from a sink into an attention system. If you're building something in this space, plan to spend as much time on the prompt that teaches the agent what to file as on the infrastructure that stores it.
