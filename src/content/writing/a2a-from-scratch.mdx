A2A (Agent2Agent) 1.0 is a protocol that lets one AI agent call another over HTTP. Most A2A demos show a request going in and an answer coming back. They skip what happens when something goes wrong: the connection drops halfway through a reply, a web page in your browser tries to call an agent running on your own machine, or the client (the program calling the agent) shows part of an answer before the agent has finished checking it. I wanted to understand those cases, so I wrote a small A2A agent server in Node.js from scratch instead of using the official A2A SDK (software development kit).

## Where a local agent can go wrong

An agent on your own machine is an HTTP server listening on localhost, and every web page you have open can send requests to localhost. Without a guard, a page can reach the agent through a cross-origin request (CORS) or a redirect. Even with a guard, an attacker can point their own domain name at 127.0.0.1, your machine's own address, so the browser treats the agent as part of the attacker's site. That trick is called DNS rebinding.

Some A2A features also make the agent fetch a web address that the caller chooses. With push notifications, the agent sends updates to an address the caller gives it. With a link attached to a message (a `url` part), the agent downloads it. Either way, the caller decides where your agent's requests go. That attack is called server-side request forgery (SSRF).

The streamed reply has its own problems. My agent, called unslop, copy-edits text and then runs a fact check to confirm the edit kept the original facts. If the client shows text while it streams in, a reader can see an edit that the fact check later rejects. And if the stream drops halfway, the client can't tell whether the task finished. For an agent meant to keep facts intact, both problems defeat the point.

## The fix: a 300-line server that handles each case

The server is `packages/mesh/src/a2a.ts` in [agent-inbox](https://github.com/shariqh/agent-inbox), about 300 lines built on Node's own `node:http` module with no framework. It runs unslop, which copy-edits public text such as PR descriptions and blog posts against a set of style rules, on a computer with a GPU at my home. The A2A server is off by default: it starts only when `A2A_ENABLED=true` is set. The [companion post](/blog/unslop-a2a-agent) covers why unslop exists and how I built it. This post covers the part of the server that speaks A2A.

**A2A 1.0 in brief.** The official definition of A2A 1.0 is a file called `a2a.proto`. It defines three standard ways to carry messages: JSON-RPC over HTTP, gRPC, and plain HTTP with JSON. An agent lists the ways it supports on its agent card (next section), and it can also name custom ones of its own. If it lists more than one, they must all offer the same operations and behave the same way. This server supports JSON-RPC only, which the spec allows.

### The agent card and the checks on every request

The agent card lives at `GET /.well-known/agent-card.json` and needs no password, like the menu taped to a restaurant door before you walk in. It tells a client what the agent supports: protocol version, capabilities, extensions, how to authenticate, and skills. A client reads it first and decides whether to send the agent any work.

Here's the card for unslop, from [`packages/mesh/src/a2a.ts`](https://github.com/shariqh/agent-inbox/blob/main/packages/mesh/src/a2a.ts):

```ts
const card = (): Json => ({
  name: 'unslop', description: 'Copy-edits public text (PR descriptions, issues, release notes, public docs, blog posts) by the unslop rules, with a fidelity check.',
  version: o.version,
  supportedInterfaces: [{ url, protocolBinding: 'JSONRPC', protocolVersion: '1.0' }],
  capabilities: {
    streaming: true, pushNotifications: false,
    extensions: [{ uri: EXTENSION, description: 'unslop task parameters and result', required: false, params: { api: 1, skillId: 'unslop', ...o.rules() } }],
  },
  securitySchemes: { bearer: { httpAuthSecurityScheme: { scheme: 'Bearer' } } },
  securityRequirements: [{ schemes: { bearer: { list: [] } } }],
  defaultInputModes: ['text/plain'], defaultOutputModes: ['text/plain', 'application/json'],
  skills: [{ id: 'unslop', name: 'unslop', description: 'Edit one public text; the result carries the check report.', tags: ['editing'] }],
})
```

`pushNotifications: false` turns off push notifications (the agent calling an address the caller supplies) on purpose, because of the SSRF risk above. The `extensions` block declares an unslop-specific add-on to A2A, named by a custom URI (`urn:agent-inbox:ext:unslop:v1`). Its settings include a SHA-256 fingerprint of the file of editing rules the agent follows. A client can compare that fingerprint with the one it expects and stop before sending anything if the rules have changed.

After the card, every request goes through one function, `handle()`. It runs six checks, always in the same order, before it does anything the request asks for. They cover the `Origin` header, the `Host` header, a secret token, a version header, a size limit and a time limit.

The `Origin` check blocks requests from web pages. Browsers always add an `Origin` header to cross-origin requests, and agent clients don't send one. So the server refuses every request that has an `Origin` header, which stops web pages from reaching the agent through CORS or a redirect.

The `Host` check stops DNS rebinding. In that attack, the browser thinks it is calling the attacker's domain, so its request names that domain in the `Host` header. The server accepts only `127.0.0.1` in `Host`, so it refuses the request.

For the token check, the client proves it's allowed in by sending a bearer token, a secret string, with each request. The server compares it with `timingSafeEqual` after checking that the lengths match. A plain `===` comparison can finish sooner when the first characters differ, and an attacker can time those answers to guess the token faster. `timingSafeEqual` takes the same time wherever the strings differ.

The server also requires an `A2A-Version: 1.0` header. The spec asks for it, and it stops programs that don't speak A2A from reaching the agent by accident. Last, request bodies are capped at 64 KiB so a huge upload can't use up memory, and requests time out after 10 seconds so stalled connections don't pile up.

### Tasks, states and the stream

A client starts work by calling `SendMessage`, or `SendStreamingMessage` to get updates as the work goes. Either call creates a task. A task is always in one of a fixed list of states: `TASK_STATE_SUBMITTED`, `WORKING`, `COMPLETED`, `FAILED`, `CANCELED`, `REJECTED`, and two states that pause for the caller, `INPUT_REQUIRED` and `AUTH_REQUIRED`. An agent can't add states of its own. To report progress, it attaches a short message to each status update it sends, such as "editing", "checking" or "retrying". The task's output is called an artifact. Messages and artifacts are both made of parts, such as a `text` part or a `data` part, and anything the agent returns beyond the edited text goes in a `data` part of the artifact.

This agent accepts exactly one piece of text from the caller: a single text part with the role `ROLE_USER`. It refuses `url` parts, which removes the second SSRF risk. A caller that wants a web page edited fetches the page itself and sends the text. Settings for a single call go in `message.metadata` under the extension URI, not in new kinds of parts.

`SendStreamingMessage` answers with Server-Sent Events (SSE): a series of small messages sent over one HTTP response. Each message is a JSON-RPC response.

```ts
res.writeHead(200, { 'content-type': 'text/event-stream', 'cache-control': 'no-store' })
const write = (events: Json[]): boolean => res.write(events.map((result) => `data: ${JSON.stringify({ jsonrpc: '2.0', id, result })}\n\n`).join(''))
write([{ task: view(t) }])
```

The stream carries **status updates only**. The edited text never appears on it. The text arrives once, in the artifact sent with `COMPLETED`, which has two parts: a `text` part with the edited text and a `data` part with the fact-check report as JSON. Because the text and its report arrive together when the task completes, a client can never show edited text before the fact check has run.

### The client

The client is [`src/unslop-client.ts`](https://github.com/shariqh/agent-inbox/blob/main/src/unslop-client.ts), written with Node's built-in modules only (no `fetch`, no SSE library). The first thing it does is read the agent card and check it: the `protocolVersion`, that the extension URI is present, and that the `api` field matches. If any of these is wrong, it stops before sending anything.

To read the stream, the client splits the incoming text on blank lines and keeps any unfinished piece for later.

```ts
onChunk: (chunk) => {
  buffered += chunk
  const events = buffered.split(/\r?\n\r?\n/)
  buffered = events.pop() ?? ''
  for (const event of events) {
    const data = event.split(/\r?\n/).filter((line) => line.startsWith('data:')).map((line) => line.slice(5).trim()).join('\n')
    try {
      if (data) take(obj(obj(JSON.parse(data))['result']))
    } catch { /* a malformed event: GetTask has the truth */ }
  }
},
```

Splitting on `\r?\n\r?\n` handles both Windows and Unix line endings. The last piece after the split may be an event that hasn't fully arrived, so it goes back into the buffer. For each complete event, the client pulls out the `data:` lines. If an event can't be parsed, the client ignores it, because the stream is only a progress feed. `GetTask` always returns the task's real state, so a garbled event loses nothing.

`GetTask` is also how the client handles a stream that drops before the task has finished. The client asks `GetTask` every five seconds and gives up after three failed requests in a row. It stops when the task reaches a final state (completed, failed, canceled or rejected) or when the client's time limit runs out. If the time limit runs out first, the client sends `CancelTask`.

The client prints the edited text only when it exits with code 0, so a shell script can capture it with `$(...)`. The other exit codes say why there's no text: 10 means the agent returned the original text unchanged, 11 that it refused the request, 12 that it was busy, 13 that the task failed, and 14 that the agent wasn't running.

## What's still open

**What I chose not to build.** Push notifications, because they make the agent fetch addresses the caller picks, which is the SSRF risk above. Multi-turn conversations, because each call here is one task, and resuming a task with follow-up messages adds work a text editor doesn't need. When I started, the server parts of the official `@a2a-js/sdk` pulled in Express and came with push notifications and database storage that I would have had to turn off, so writing on `node:http` directly was faster. Since then, SDK 1.3.0 added `JsonRpcTransportHandler`, which handles JSON-RPC without tying you to a framework, so switching to it is on my to-do list as [issue #498](https://github.com/shariqh/agent-inbox/issues/498).

**What a security review found.** It found four bugs, and all four are fixed:

- **A leaked API key.** Some Node error messages include the value that caused the error. When that value was a URL with an API key in it, the key ended up in the logs.
- **A double slash in a URL.** Joining two strings produced a backend URL with `//` in its path. Some proxies read `//path` as a new host name and send the request to a different server.
- **A timer that fired too late.** After an error had already ended a request, a timeout could still fire and run against half-set-up state.
- **Terminal control codes.** The client printed status messages from the agent without removing terminal control codes, so a malicious agent could change what the terminal shows.

One gap remains. The client can't yet prove it's talking to the real agent. If another program takes the agent's port before the agent starts, the client sends its token to that program instead. That's [issue #492](https://github.com/shariqh/agent-inbox/issues/492).

The full server is at [`packages/mesh/src/a2a.ts`](https://github.com/shariqh/agent-inbox/blob/main/packages/mesh/src/a2a.ts) and the client at [`src/unslop-client.ts`](https://github.com/shariqh/agent-inbox/blob/main/src/unslop-client.ts). User docs for the unslop agent are in [`docs/unslop.md`](https://github.com/shariqh/agent-inbox/blob/main/docs/unslop.md).

I'd make the same three choices again: send only status updates on the stream, deliver the edited text once when the task completes, and refuse `url` parts before a request reaches the editing code. Each one rules out a kind of failure up front instead of patching it later.
