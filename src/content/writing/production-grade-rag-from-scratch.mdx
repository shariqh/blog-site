Every "Sources" panel in a RAG product looks identical, whether the answer actually used those sources or not. That gap — between what got retrieved and what shaped the response — is the one that cost me a release cycle, right up until I stopped treating citation display as a formatting detail and started treating it as its own pipeline stage.

Retrieval quality alone doesn't get a RAG system to production. Tenant isolation, bounded history, evidence gating before generation, citation parsing after generation, and evaluation discipline all have to hold at the same time, or the gaps between them surface as user-facing trust failures. Here's how I'd build the whole system from scratch, using Askdocs as the running case study.



## Tenant isolation and ingestion

Every query in Askdocs is scoped to a tenant. Isolation is enforced at index time, not by a filter added at query time. Each document is ingested with a tenant identifier baked into its vector namespace and into every BM25 shard.

Two things follow from this. First, the same retrieval stack runs across tenants without cross-contamination. Second, alias coverage gets pushed into ingestion. A user asking about "Notes app", "Apple Notes", and "the notes integration" should hit the same document. Alias expansion built into the index means you don't pay for it in latency on every query.

The ingestion pipeline also produces a SHA-pinned snapshot. Exact-SHA deployment isn't just discipline — it's the only way to make retrieval reproducible for evaluation. If your index drifts between when you run holdout cases and when you deploy, your metrics are unreliable.

## Two signals, one ranking pass

Sparse lexical retrieval (BM25) and dense vector retrieval are complementary. BM25 excels on exact term matches: product names, error codes, CLI flags. Dense retrieval handles paraphrases and semantic variants. Running only one means systematically missing the other's wins.

Askdocs runs both in parallel, then combines ranks. BM25 results are cached; the lexical index is expensive to build and rarely needs rebuilding per query. Vector retrieval runs against the current snapshot. Reciprocal rank fusion (RRF) combines them into a single ordered candidate list.



After ranking, two filters run before any candidates reach the prompt.

**Deduplication by page, then by content.** A 512-token chunk and a 256-token chunk from the same page can both rank highly. Without dedup, the same paragraph appears twice in context, wasting tokens and diluting attention.

**Per-page diversity cap.** After dedup, a single highly-relevant page shouldn't crowd out five others. Enforce a candidate limit per source page. This matters most on aggregation queries that span the whole corpus rather than one document — without a cap, the ranked list clusters on whichever page has the most chunks, and the answer only reflects that one source instead of the full breadth the question needed.

## Bounded history without trusting the assistant

RAG queries aren't stateless. Including conversation history helps; including the wrong history poisons the retrieval signal.

The Askdocs history window is bounded by recency and by message role. **Only user messages factor into retrieval history.** Assistant turns are excluded.

If the assistant made a mistake in turn 3, pulling that response into turn 4's retrieval context propagates the mistake. User messages represent what the user wants. Assistant messages represent what the model produced, which may contain errors that then bias retrieval toward the wrong documents.

Most RAG implementations concatenate the full conversation and notice retrieval degrading a few turns in. Scoping history to user turns, with a hard recency limit, keeps the retrieval signal clean.

## Evidence gates and abstention before generation

The most expensive call in a RAG pipeline is generation. The second-most expensive outcome is a confidently wrong answer. Evidence gating before the LLM call addresses both.

Before sending any candidates to the model, the pipeline checks:

- **Exact phrase coverage**: does any candidate resolve to the queried entity's canonical identity — via the same alias index built at ingestion, not a fresh substring match — rather than just a semantically nearby chunk?
- **Relation evidence**: if the query implies a relationship (A supports B, A connects to B), is there evidence of that specific relation in the candidates, or just co-occurrence?

Co-occurrence is the subtle failure mode. A document mentioning "Obsidian" and "Apple Notes" in adjacent paragraphs will rank highly for "Apple Notes to Obsidian" even if it never asserts they're connected. Without a relation gate, you'll generate a confident answer about a workflow that doesn't exist.

If the evidence gates fail, the system returns `insufficient_evidence` without calling the LLM. Cheap, and correct.



## Candidate citations vs. used citations

"Sources" in a RAG UI typically shows what was retrieved. The model's answer draws on a subset of that. A user reading five source links expects all five to support what was said. If the model cited only sources 1 and 3, sources 2, 4, and 5 are noise at best.

Askdocs separates retrieval candidates (what went in) from used citations (what came out). After generation, a safe parser extracts inline citation markers, validates each against the candidate list, and resolves them to authoritative URLs. Any marker that doesn't resolve gets stripped server-side rather than served broken.

The "Sources" section in the UI shows only resolved, used citations. What you see corresponds to what was actually cited.

Marker dedup runs before resolution, not after. If the model cites the same source in two different sentences, the parser collapses that to one entry in the sources list instead of showing the same link twice. Small, but trust erodes around exactly this kind of inconsistency.

## Response states

Three states, rendered distinctly in the UI:

- **Grounded**: indexed evidence exists, inline citations resolve, used sources are present.
- **Corrected**: the user's premise was wrong (e.g., implied a relationship that doesn't exist), and the answer corrects it with evidence.
- **Insufficient**: evidence gates didn't pass or coverage was too sparse. No generation call was made.

Insufficient is a hard gate, not a soft "couldn't find anything." Users calibrate trust differently when a system is explicit about what it doesn't know.

When a response needs correction, the supersession is non-destructive: original and corrected responses are both stored, with the correction flagged. The audit trail stays intact and correction rate becomes a meaningful metric over time.

## Evaluation discipline

Evaluation runs on two case sets. Twenty calibration queries tune retrieval parameters during development; ten holdout queries are only consulted before release. You cannot tune against your holdout. Once you start adjusting to pass holdout cases, the metric means nothing.

Metrics tracked across both sets:

- **hit@1, hit@3**: correct source in top 1 or top 3 candidates
- **MRR**: mean reciprocal rank across the full query set
- **Coverage**: fraction of queries returning grounded or corrected
- **Abstention rate**: fraction returning insufficient (too high signals over-conservative gating; too low signals under-gating)
- **Calibration**: do confident responses correspond to correct ones?

The Askdocs release shipped with 325 tests passing: retrieval unit tests, pipeline integration tests, citation parsing edge cases, SSE streaming compatibility. That count is a forcing function. When retrieval parameters change, 325 tests tell you exactly what broke.

Pre-release smoke: one bounded request against the hosted model, checking p50/p95 latency and cost per query. A sanity check that the endpoint is alive and within budget, nothing more.

The per-page diversity cap fix, described above, was caught during calibration, not after release. Real failure transcripts, frozen into calibration cases, drive systematic improvement more reliably than any amount of synthetic query generation.

The Askdocs source is at [github.com/shariqh/askdocs](https://github.com/shariqh/askdocs) if you want to dig into specifics.

None of these pieces is optional once you're serving real tenants. A hybrid retriever with no isolation boundary leaks data across accounts. Evidence gates with no citation parser produce answers a user can't verify. Citation parsing with no evaluation discipline drifts silently as the index changes underneath it. A production-grade RAG system is what happens when all of it holds at once — not a better embedding model, but a product built with the same rigor as the rest of your system.
